# Validation of Trigger Compilation (Phase 2\)

# Automatic LLM-based Validation 

The validation performed during trigger generation was only static. 

The LLM verified:

* Relevant rules and insertions into `rdf_rule_contribution`;  
* one insertion into `rdf_maintenance_queue`;  
* use of `deleted_R`  and `inserted_R`;  
* presence of `RETURN NULL`;  
* correspondence between the joins and the relational schema;  
* Transformation Rule URIs and RDF datatypes;  
* named-graph URIs   
* absence of GraphDB or SPARQL operations inside the trigger.

## Semantic Validation of Rule Contributions

The generated triggers are validated using controlled relational updates and manually established reference results. For each update, the validation first checks whether the trigger identifies exactly the set of relevant Transformation Rules.

The validation is then conducted at two levels:

1. **Validation of the generated maintenance code.** For each relevant rule (\\Psi), the generated SQL code that computes its contribution is reviewed against a corresponding reference implementation designed by a human. This comparison verifies the implementation of the rule semantics, including selection conditions, relational paths, affected pivot tuples, URI construction, RDF term construction, and the separation between pivot-relevant and relation-relevant computations.  
2. **Validation of the generated maintenance information.** The update is executed on a controlled database state, and the rule contribution published in the maintenance queue is compared with the manually computed expected result. Depending on the relevance and type of (\\Psi), the comparison includes (A^-*\\Psi(u)), (A^+*\\Psi(u)), (\\Delta^+*{\\mathrm{pivot}}\\Psi), (S\_2\\Psi), (\\Delta^+*{\\mathrm{rel}}\\Psi), and (\\Delta^+\\Psi). Rule identifiers, relevance types, relational paths, RDF templates, datatypes, and named-graph URIs are also verified. JSON arrays are compared as sets, independently of element order.

A test succeeds iff the trigger publishes exactly one contribution for every relevant rule, publishes no contribution for an irrelevant rule, and every published contribution equals its manually computed expected value.

# Automated Semantic Validation by Complete Recomputation

This is the most important validation step.

For each test scenario:

1. Preserve the pre-update database state \\(\\sigma\_0\\).  
2. Completely compute the RDF quads generated by the relevant rules over \\(\\sigma\_0\\).  
3. Execute the relational update.  
4. Completely compute the RDF quads over the post-update state \\(\\sigma\_1\\).  
5. Compute the expected changeset:

Delta- \= W0 \-  W1 

Delta+ \= W1 \-  W0  

6. Process the contributions generated by the trigger and the asynchronous worker.  
7. Compare the incremental result with the expected changeset as sets, ignoring the order of JSON array elements.

The test passes only when the incremental changeset equals the changeset obtained from a complete recomputation.

This comparison should be considered the main correctness criterion for the experiment. It used selected updates: a list with one insertion, one deletion, and one update per selected relation, along with their expected changesets.

A separate update is not required for each relevant Transformation Rule. Since the generated trigger is a statement-level trigger, every update on relation (R) executes the same maintenance procedure and computes a contribution for every rule in (Relev(R)). The resulting contributions depend on the deleted and inserted transition tuples and on the current database state, including the affected pivot tuples and the tuples reachable through the relational paths.

Therefore, the validation does not associate one update with each rule. Instead, it uses controlled database states and update statements that, together, ensure that the relevant selection conditions and relational paths are evaluated. A single update statement may validate several or even all relevant rules, provided that the test database contains the required related tuples and that both non-empty and condition-dependent contributions are adequately covered.
